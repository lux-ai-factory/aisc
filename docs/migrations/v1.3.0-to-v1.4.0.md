# Migrating from v1.3.0 to v1.4.0

**From:** `v1.3.0` (released 2026-09-25, the latest tag)
**To:** `v1.4.0` — **provisional / unreleased**. Source of truth is the branch
`integration/int-01-frozen-unified-app` (tip `33e1d3e`), being merged to `master` in
[draft PR #125](https://github.com/lux-ai-factory/aisc/pull/125).

**Audience:** plugin authors (human or agent) updating a plugin for the new release, and agents
maintaining the platform.

---

## 0. Do I need to change anything?

| surface | change | breaking? |
|---|---|---|
| `shared/plugin-interface` | **0.5.0**: the adapter mechanism (`aisc_plugin_interface.adapters`), `@evaluation_input` `accepts`/`role`/`adapter`/`env` fields, `EndpointConfig`, and **input providers removed** (use data adapters, §1.3); also **0.4.0**: generic input providers, `facet_by_dimension`, the report ABI | **BREAKING** only if you pass `input_provider_class=` — see §1.3 |
| `shared/plugin-manager` | **0.4.0**: adapters and presets are discovered in plugin and adapter-only packages (`list_adapters`/`load_adapter`); also the bundled `def_plugins/` scan, empty-version = latest, no cwd scan | **additive** |
| `apps/eval` (where your plugin runs) | the child environment is a **closed allowlist**; a run-local run withholds target secrets; dispatch is **self-contained** (no mid-run backend fetch); outbound data is scrubbed; **an endpoint input is reached through a run-local door** (§3.5) | **BREAKING** if your plugin reads environment variables, calls the backend during a run, or takes a target URL/key from its own config — see §3 |
| `apps/backend` (API) | new endpoints, optional versions, richer audit metadata; **`/connections`, `/helpers`, `/run-bindings` are removed** and `Connection`/`Helper`/`RunBinding` tables are dropped (§4.1) | **BREAKING** for tooling that calls them |
| `apps/webapp` | internal React only | none |

**Short version:** a plugin that (a) reads its inputs through the declared `@input` providers,
(b) takes all its settings from plugin config / project settings, and (c) does not talk to the
backend mid-run, **keeps working unchanged**. The one thing that will break a plugin is
depending on environment variables that used to be inherited (§3.1).

Package versions: **`aisc-plugin-interface` is now `0.5.0`** (it gains the adapter mechanism and the
new slot fields, §1.3) and **`aisc-plugin-manager` is now `0.4.0`** (adapter discovery, §2). Raise your
dependency lines to `>=0.5.0` / `>=0.4.0`. These are lower bounds, not pinning behaviour: a plugin you do
not rebuild keeps working on the version it was already installed with.

---

## 1. Plugin interface (`aisc-plugin-interface`)

> **0.5.0 removes input providers.** `BaseInputProvider` and the `Csv`/`Parquet`/`Onnx`/`Json` providers
> are gone, and `@evaluation_input(input_provider_class=...)` no longer exists. Data adapters do the same
> job (and met the providers' 0.4.0 changes below). If you pass `input_provider_class=`, see **§1.3** to
> migrate — otherwise nothing in this section applies to you.

The 0.4.0 provider changes below are historical; providers were removed in 0.5.0.

- **`BaseInputProvider` is now generic:** `class BaseInputProvider(ABC, Generic[T])`.
  - `__init__(self, file_content: bytes | Path | T)`
  - `_read_data(self, file_content: bytes | Path | T) -> T` (was `bytes) -> Any`)
  - `get_data(self) -> T` (was `-> Any`)
- **Input content may now be a `Path` or already-parsed data**, not only raw bytes:
  - `BaseEvaluationPlugin.set_input_content(name, file_content: bytes | Path | Any | None)`
  - `BaseEvaluationPlugin.parse_config_from_dataset(file_content: bytes | Path | Any)`
- **`CsvInputProvider`** is now `BaseInputProvider[list[dict]]` and handles a `Path` (it reads
  the file itself) and an already-parsed `list[dict]` (passthrough). `OnnxInputProvider`,
  `ParquetInputProvider` and `JsonInputProvider` still take `bytes`.
- **`MetricVisualization.facet_by_dimension: list[str] | None`** — split a chart into one plot
  per value of these dimensions (within each plot, `group_by_dimensions` stay the series).

> The runtime today still passes raw `bytes` to `set_input_content` (the worker reads the tmp
> file and hands over the bytes). The wider types are opt-in: accept a `Path` **only if** you
> want the provider to read the file itself. If you do nothing, you keep receiving `bytes`.

**Optional, if you want it:** make your provider accept a path instead of forcing the caller to
read the file:

```python
class MyProvider(BaseInputProvider[MyData]):
    def _read_data(self, file_content: bytes | Path | MyData) -> MyData:
        if isinstance(file_content, MyData):
            return file_content
        if isinstance(file_content, Path):
            file_content = file_content.read_bytes()
        return MyData.parse_raw(file_content)
```

### 1.1 Optional: draw your plugin's section of a report

A report's **Test results** block prints one section per plugin run. By default the backend draws
a generic measurements table for your run. You can replace it with your own renderer by
implementing one method:

```python
from aisc_plugin_interface import BaseEvaluationPlugin
from aisc_plugin_interface.report import BaseToolRenderer, ToolRun


class MyReportRenderer(BaseToolRenderer):
    def render(self, run: ToolRun, ctx) -> str:
        return self.render_package_template("report/section.html.j2", run=run, t=ctx.t)


class MyPlugin(BaseEvaluationPlugin[MyConfig]):
    def get_report_renderer(self):
        return MyReportRenderer()
```

- `ToolRun` is read-only: `run.tool`, `run.measurements`, `run.observations`, `run.components`,
  `run.artifacts`, `run.evaluation`, `run.evaluation_plugin`. Do not touch a database — you are
  handed the run's frozen data.
- The renderer's templates are found in **your package folder** (the folder of the module the
  renderer class is defined in); `render_package_template("report/section.html.j2", ...)`
  auto-escapes the result.
- Optional hooks: `.charts(run)` and `.headline(run)` let the report's chart and key-figure blocks
  use your numbers; `.verdict(run)` returns `"pass"` / `"fail"` / `None`.
- `get_report_renderer()` is **optional**. Return `None` (the default) — or let it raise — and the
  report still shows your run, through the generic measurements table. Nothing breaks for a plugin
  that predates this contract.

The ABI (`BaseToolRenderer`, `ToolRun`, the `i18n` / `templating` / `charts` helpers) lives in
`aisc_plugin_interface.report`, behind the `[report]` extra. A plugin that draws a section
therefore depends on `aisc-plugin-interface[report]>=0.4.0`.

> **Platform note (release step).** The backend image installs `aisc-plugin-interface` from PyPI and
> is built with `uv sync --frozen`, so `apps/backend/uv.lock` pins the version. Publishing
> `aisc-plugin-interface` **0.4.0** and regenerating that lock (`uv lock` in `apps/backend`) must
> happen before the backend image builds; until then the lock is unsatisfiable (the extra only
> exists from 0.4.0).

### 1.2 Migrating a plugin that already drew its own report section

Before this release a plugin's report section could come from a **separate distribution** — the
pilot's `aisc-report-plugin-<tool>` package, discovered through the backend's `aisc_report.tools`
entry point (and, for langbite / mlareject / promptfoo / strongreject, from packages the backend
**bundled** as `aisc_report_plugin_*`). Both paths are gone: the fragment renderer now lives
**inside the eval plugin** and is reached through `get_report_renderer()`. To move a renderer:

1. Move the renderer's code into a `report/` subpackage of your plugin package (next to `plugin.py`):
   `renderer.py`, any `parsing.py`/`statistics.py`, its `templates/` and any `i18n/` catalogues.
2. Repoint its imports from `aisc_report_plugin_interface` to `aisc_plugin_interface.report`
   (the ABI moved verbatim; `charts` / `i18n` / `templating` keep their module paths under
   `aisc_plugin_interface.report.*`).
3. Implement `get_report_renderer()` on the plugin class, returning your renderer instance.
4. Depend on `aisc-plugin-interface[report]>=0.4.0` and drop the `aisc_report.tools` entry point
   from your `pyproject.toml`.
5. Run the report for a run of your tool and confirm your fragment is drawn (the backend logs and
   falls back to the generic table if the renderer raises).

The pre-move sources of the four tools that were bundled are kept for reference under
[`SCRATCH-report-plugins/`](../../SCRATCH-report-plugins/README.md) (scratch, not binding); the
langbite / promptfoo / strongreject renderers have already moved into their plugin repos.

### 1.3 Adapters and slots (ADR 0009)

A plugin declares its inputs with `@evaluation_input`; the **shorthands still work unchanged**
(`input_type=LLM`, `DATASET`, `MODEL`, `DATASHAPE`, `RESOURCE`). What is new:

- **Slot fields (all optional):** `accepts` (the value types or face protocols the slot uses),
  `role` (`subject` | `instrument` | `input`), `adapter` (the default adapter id),
  `adapter_required` (lock the choice) and `env` (a mapping of environment variables rendered with
  `{base_url}`, `{api_key}` and `{model}`). `InputDefinition` gained the same fields with defaults, so a
  definition serialised before this contract still parses.
- **`aisc_plugin_interface.adapters`:** the adapter mechanism. A `DataAdapter` turns a file format into a
  value the slot accepts; an `EndpointAdapter` turns a target's protocol into the face the plugin speaks.
  The standard library (csv/tsv/parquet/jsonl/json/onnx data; openai/oip/rest/a2a endpoint) ships with the
  interface.
- **`get_endpoint(name)`** returns an `EndpointConfig` (`url`, `protocol`, `model`, `token_key`) for a
  non-`openai-chat` endpoint slot; `get_llm_config(name)` is unchanged for an `openai-chat` slot.

**A plugin may ship an adapter.** Put the `DataAdapter`/`EndpointAdapter` subclass (and any `Preset`) in the
package's module folder; the plugin manager discovers it (`list_adapters`) and the worker imports it from
the same package at run time. No new entry point or dependency is needed beyond `aisc-plugin-interface`.

**Migrating from `input_provider_class=` (breaking, 0.5.0).** Input providers were removed — the standard
data adapters do the same job, and keeping both was one concern implemented twice. A slot no longer names a
provider class:

```python
# before
@evaluation_input(name="dataset", label="Dataset",
                  input_provider_class=CsvInputProvider, input_type=InputType.DATASET)
class MyPlugin(BaseEvaluationPlugin[Config]):
    def evaluate(self, config_data):
        rows = self.get_input_data("dataset")   # the provider parsed the bytes

# after — declare the value type; the runtime picks the adapter and parses
@evaluation_input(name="dataset", label="Dataset",
                  input_type=InputType.DATASET, accepts=["records"])   # ["table"] for a DataFrame
class MyPlugin(BaseEvaluationPlugin[Config]):
    def evaluate(self, config_data):
        rows = self.get_input_data("dataset")   # list[dict], produced by the adapter
```

`get_input_data(name)` returns the produced value directly (no provider wrapper). A format the standard
library does not cover — a bespoke CSV shape, a predictions file — becomes a **plugin-shipped
`DataAdapter`** (give the slot its id with `adapter="<id>"`), not a provider class.

## 2. Plugin manager (`aisc-plugin-manager`)
- **Bundled plugins.** `def_plugins/` (shipped with the platform, mounted by the
  `plugin_downloader` compose file) is now scanned alongside `plugins/`.
- **An empty version means "latest".** `Loader.load_package(package_name, version=None)` — and
  the install/update endpoints — resolve an empty/`None` version to the highest discovered
  version (`packaging.version.parse`). Before, the caller always had to name a version.
  *If you relied on a specific version, pass it explicitly* — the default changed from "must
  name one" to "latest".
- **An empty local plugin path no longer scans the working directory.** The loader used to add
  `Path("")` (the cwd) as a plugin folder; now an unset/blank path adds nothing.

The **packaging convention is unchanged**: your package must declare a dependency containing
`aisc-plugin-interface`, ship a module folder matching the package name, and carry
`project.name` + `project.version` in `pyproject.toml`.

## 3. Evaluation runtime (`apps/eval`) — the breaking part

### 3.1 The plugin child environment is a closed allowlist ⚠️ BREAKING

Your plugin runs in a subprocess whose environment is **only** these variables (plus whatever
you declared):

```
PATH  HOME  LANG  LC_ALL  TMPDIR  TZ  UV_CACHE_DIR  UV_PYTHON
```

A plugin is treated as untrusted catalogue code, so no worker credential (database, registry,
Keycloak) is passed to it. **Anything else you used to read from the environment is gone** —
`HF_HOME`, `TRANSFORMERS_CACHE`, `AWS_*`, `HTTP_PROXY`/`HTTPS_PROXY`, `CUDA_VISIBLE_DEVICES`,
`OPENAI_API_KEY`, custom `MY_PLUGIN_*` vars, and so on.

**Do this instead:** declare the value as plugin config or a project setting and read it from
the plugin API — not from `os.environ`.

```python
# before
token = os.environ["MY_PLUGIN_TOKEN"]

# after — declared in the plugin's config model / project settings
token = self.config.my_plugin_token
```

Declared **secrets** are still delivered, under a deterministic name:
`AISC_SECRET_` + the plugin config key (or the project config key) upper-cased with every
non-alphanumeric character replaced by `_`. E.g. key `openai_api_key` →
`AISC_SECRET_OPENAI_API_KEY`. Read those if you specifically need the env form.

### 3.2 A run-local run withholds target credentials

When a run executes **local / native** (on the worker's own host, beside the system it
assesses), the target's per-run credentials are withheld from the child entirely, so the run
cannot exfiltrate the target's key. If your plugin needs the target's credential, it must run
as a normal (non-local) run.

### 3.3 Dispatch is self-contained — no mid-run backend fetch

The worker no longer calls the backend while a run is in flight. Inputs (dataset/model bytes),
project settings and plugin-status are all resolved **at dispatch time** and handed to the
worker. If your plugin fetched backend data during a run (directly or via a helper), that call
is now gone: move the value into plugin config / project settings so it arrives with the run.

### 3.4 Outbound data is scrubbed

Stdout, stderr and produced artifacts pass through the outbound scrubber (I7) before they leave
the worker. Do not rely on the platform echoing a raw secret back to you.

### 3.5 Endpoint inputs go through a run-local door (ADR 0009)

An `openai-chat` (or other endpoint) input is no longer handed to the plugin as the target's URL and key.
The worker starts a **run-local door** in the plugin's own venv and gives the plugin:

```python
llm = self.get_llm_config("target")
# llm.endpoint_url -> http://127.0.0.1:<port>/<slot>   (the door, not the target)
# llm.secret_key   -> a run token key; self.get_secret(llm.secret_key) returns the token
```

The plugin builds its OpenAI client against `llm.endpoint_url` as before; the door holds the real key,
forwards the call, checks the project's allowed-hosts rule and scrubs the key from the answer. The target
key is **never** in the plugin's environment or its input file. A plugin that took the target URL/key from
its **own** plugin config keeps working, but without the door (see the catalogue follow-up in the plan);
to get the door, declare an endpoint slot instead.

## 4. Backend API (`apps/backend`)

Additive; relevant if your tooling or a plugin helper calls the API.

- **Plugin version management (new):**
  - `PATCH /plugins/{plugin_pid}/version` — switch the project's plugin(s) of a package to
    another available version (history-preserving: the old rows are soft-disabled, the target
    rows enabled, so evaluation/config history stays attached to its version). Audited.
  - `POST /plugins/{plugin_pid}/update` — update from the catalogue; an empty version picks the
    latest, a version pins it exactly like the PATCH.
- **Install** accepts an empty version, meaning the latest available.
- **Audit metadata** on evaluation/plugin events now carries `projectPid` and `source_app`
  (e.g. `"eval"`), in addition to the previous fields.
- **Project-scoped routes now deny by default:** a caller who is not a member of the project
  gets `404`, and a member below the needed rank gets `403`. Evaluation and stored-file reads
  are bound to the owning project.
- **New routers** (additive, no removals): allowed-hosts, evidence, reports, qualification,
  questionnaire, control-objectives, controls, catalogue, results, stats, task, authz, admin-users.

### 4.1 Components and adapters (ADR 0009)

`Connection`, `Helper` and `RunBinding` are gone; everything a run can use is an `AIComponent`, and what a
run used is recorded on its `EvaluationInput`.

- **Removed routes:** `GET/PUT/DELETE /projects/{pid}/connections*`, `/projects/{pid}/helpers*`,
  `/projects/{pid}/runs/{plugin}/bindings*`. Use the component routes instead.
- **Removed tables:** `aisc_backend_connection`, `aisc_backend_helper`, `aisc_backend_runbinding`
  (a best-effort data migration folds their rows into endpoint components and re-keys their secrets; only
  mainline data needs preservation). `AllowedHost` and `/allowed-hosts` stay.
- **New catalogue endpoints:** `GET /adapters` and `GET /presets` (the adapter/preset catalogue from the
  plugin manager); `GET /plugins/{pid}/slots/{name}/candidates` (the components that may fill a slot, with
  the adapters that fit each); `GET /projects/{pid}/endpoints` (project-level endpoints).
- **Components CRUD** accepts a preset payload (`{preset, fields}`) or an advanced payload
  (`{component_type: "endpoint", protocol, url, adapter, adapter_config, secret}`). `POST /components/{pid}/test`
  replaces "test connection". The evaluation-create body accepts `adapter`/`adapter_config` per input.
- **One report renderer (ADR 0008).** Report rendering is the single in-process engine; the
  external `REPORT_SERVICE_URL` seam and the `apps/report` service are gone. A `pdf`/`docx`/`html`
  request always renders in the backend, and each plugin's per-tool section is drawn by the eval
  plugin itself (§1.1) with the generic measurements table as the default. Deployers: drop any
  `REPORT_SERVICE_URL` and the report container.
- **Keycloak Admin client.** The backend manages users through a confidential Keycloak
  service-account client (`aisc-backend-admin`, realm-management `realm-admin`) rather than a
  user's password. The realm template imports the client and the compose files wire
  `KEYCLOAK_ADMIN_URL` / `KEYCLOAK_REALM` / `KEYCLOAK_ADMIN_CLIENT_ID` /
  `KEYCLOAK_ADMIN_CLIENT_SECRET` (what the backend sends to obtain a token) and
  `BACKEND_ADMIN_CLIENT_SECRET` (substituted into the imported realm) — the two secrets must
  match. With no secret the admin surface is off.

## 5. Webapp (`apps/webapp`)

No plugin-facing change — the work here is the React shell, the Collect-evidence hub, the
evidence/report pages and the pilot look. The **Connections** and **Helper models** pages are gone:
components (with a preset chooser and a custom endpoint form) and the **AI assistant and judge models**
section now live under **Settings**, together with **Allowed internal hosts**. Nothing a plugin imports.

## 6. Checklist for plugin authors

- [ ] Grep your plugin for `os.environ` / `os.getenv` and move every value it needs into plugin
      config or project settings (§3.1).
- [ ] Grep for any backend/HTTP call made **during** `evaluate` — remove it; supply the value at
      dispatch time via config (§3.3).
- [ ] If the plugin needs a target credential, confirm it is not expected to run **local** (§3.2).
- [ ] If you used `input_provider_class=`, migrate to `accepts` (and a plugin-shipped `DataAdapter` for a
      bespoke format) (§1.3).
- [ ] Optional: implement `get_report_renderer()` to draw your own report section (§1.1); do nothing
      and the report falls back to the generic measurements table.
- [ ] Run the plugin through the platform (or `apps/eval`'s test harness) and confirm the run
      completes with only the allowlist environment.

## 7. Testing your updated plugin

```bash
# the plugin loads and runs under the platform's own harness
cd apps/eval && uv run python -m pytest tests -q

# end to end: install the plugin in a project and run an evaluation, then check
# the run completed and its artifacts/measures arrived
```
